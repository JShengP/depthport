**Status: experimental v0.3 diagnostic tool. Not a validated MOT benchmark, not a camera tracking speed test, and not metric 3D accuracy.** Evaluates a local `tracking.json` generated by the existing session tracking pipeline against manually reviewed `ground_truth.json`. It **never** invokes a model, records video, sends data online or modifies the stored session. Optional synthetic examples are deliberately not real YOLO results.

## Real-video pilot — 2026-10-17

An initial local research run used all **179 consecutive frames** of the official compressed [MOT15 TUD-Stadtmitte video](https://motchallenge.net/data/MOT15/), with the supplied 1,156 GT boxes. Genuine YOLO26n person detections were cached once on CPU (confidence 0.1, NMS IoU 0.7, maximum 20 objects); every candidate received the identical boxes and frame order. [Aggregate evidence, hashes, exact configurations and all eight results](../validation/v0.3-tracking-pilot.json).

Pinned [TrackEval](https://github.com/JonathonLuiten/TrackEval/tree/12c8791b303e0a0b50f753af204249e622d0281a) evaluated the existing association, Ultralytics ByteTrack/BoT-SORT and five lightweight [Roboflow Trackers](https://github.com/roboflow/trackers) implementations. Selected observations:

- Existing DepthPort association: **34 ID switches**, IDF1 **50.16%**, recall **86.33%**.
- Roboflow ByteTrack: **23 ID switches**, IDF1 **69.19%**, recall **81.40%**.
- Roboflow BoT-SORT: **7 ID switches**, IDF1 **81.01%**, recall **81.57%**.

This makes Roboflow BoT-SORT a useful next candidate on this clip. Lower switch counts alone are insufficient: recall also decreased. Tracker defaults and activation thresholds differ; only frame rate was set to 25 for the Roboflow candidates. No tuning or ReID was used. One short training clip, re-encoded as MP4, is **not a full MOT benchmark or evidence of a general winner**. The supplied GT can include occluded targets; no separate visible-only or per-scenario annotation audit was performed.

Separately, **24 consecutive frames (78–101)** passed the actual bounded Session flow: genuine DA V2 Small CUDA depth, bundle integrity, saved RGB/depth/point-cloud replay, temporal consistency, and CPU YOLO26n Detect/Segment tracking. Detect produced 172 observations over 19 IDs; Segment produced 159 over 16 IDs. Saved depth remained relative/virtual and camera XYZ finite. These are execution checks with estimated intrinsics, not metric 3D truth. The Session diagnostic scores in the JSON use the existing experimental evaluator and must not be mixed with the dense TrackEval scores.

Roboflow `trackers==2.6.1` exposes `supervision.Detections` and uses Apache-2.0 code. Its NumPy >=2.0.2 requirement conflicts with the current DA3 NumPy <2 recipe, so the comparison ran in an **isolated NumPy 2.2.6 environment**, with `supervision==0.27.0`; the four-model environment retained NumPy 1.26.4. Integration needs a separately validated dependency migration or worker boundary. McByte's optional mask models were not installed or evaluated.

The MOT15 data is used locally for non-commercial research under its [CC-BY-NC-SA-3.0 notice and original-source conditions](https://motchallenge.net/data/MOT15/). No video, GT, per-frame boxes/IDs, session bundles or runtime logs are published here. v0.3 Alpha remains an experimental development preview while broader scene and physical-camera acceptance continues.

## Why

A track ID staying stable in a synthetic test does not prove reliability on a real sequence. Use labeled sequences that intentionally include:

- **Entry/exit:** people or objects enter or leave the field of view.
- **Missed detection:** visible objects that the tracker/detector fails to associate.
- **Partial occlusion / reappearance:** an object is hidden and later becomes visible.
- **Crossing / overlap:** two same-class objects exchange left/right order.
- **Fast motion, illumination changes, and camera motion:** annotate as appropriate.

A complete occlusion with no reliable visible-box GT can be represented by a frame with `"evaluated": false` (the entire frame is skipped), rather than inventing ground-truth bounding boxes. A partially occluded but visible object can remain in GT with the `occlusion` tag.

## How to obtain the tracking report

Use the **same authorized and locally captured sequence** under `http://127.0.0.1:8000/sessions`: enable `ENABLE_SESSION_STORAGE=1`, explicitly save 2–24 depth-inferred frames, run **Analyse saved frames** with YOLO Detect/Segment, and download `tracking.json`. The saved frame's `index` is the join key; **not** a free-running video frame number. Never confuse the synthetic test fixtures with an actual pretrained YOLO run.

**Important sampling caveat:** v0.3 captures frames on explicit button presses. These snapshots may be **widely or irregularly spaced**, and YOLO prediction is rerun on each snapshot. They cannot establish full-FPS MOT performance or frame-level occlusion recovery under dense video. For a valid ByteTrack/BoT-SORT comparison, capture an *authorized, densely labeled video sequence*, run each candidate on the **same ordered frames and detector/checkpoint/configuration**, then convert its predictions into the same report format or evaluate with established MOT tooling.

## Ground Truth format

Create a local UTF-8 JSON file with the same session ID:

```json
{
  "format": "depthport.tracking-ground-truth.v1",
  "session_id": "<session UUID copied from tracking.json>",
  "frames": [
    {
      "index": 1,
      "tags": ["normal"],
      "objects": [
        {"gt_id": "person-A", "class_id": 0, "bbox": [10, 20, 100, 180]}
      ]
    },
    {"index": 2, "tags": ["occlusion"], "evaluated": false, "objects": []}
  ]
}
```

- `sampling` (optional): `manual_sparse`, `dense_video`, `synthetic_example_not_real_video`, or `unspecified`. Self-declared for audit only; not independently verified.
- `index`: an existing **saved session frame** number, unique per annotation file. You may annotate a subset of frames, but must report the subset and its limitations.
- `gt_id`: stable *manual annotation ID* across visible occurrences; not a person's real identity or biometric label.
- `bbox`: `[xmin, ymin, xmax, ymax]`, pixel coordinates aligned to the **saved `rgb_aligned.png` image**, not the original camera pixel dimensions. Keep `class_id` consistent with YOLO classes.
- `tags` (optional): `normal`, `entry_exit`, `occlusion`, `crossing`, `fast_motion`, `low_confidence`, `lighting_change`, `camera_motion`. Annotators must define these labels consistently.
- `evaluated=false` (optional): exclude frames whose annotations cannot be reliably scored (e.g. full occlusion). Skips must be reported; do not hide difficult visible examples to inflate scores.
- Empty `objects` on an evaluated frame means **no visible objects** and predicted objects become FP. Unlabeled objects in an evaluated frame can also appear as false positives.
- Maximum 24 annotated frames in this version, 64 GT and 64 predictions per frame.

## Run the evaluation

```bash
python tools/evaluate_tracking.py \
  --tracking outputs/sessions/<session-id>/tracking.json \
  --ground-truth /path/to/ground_truth.json \
  --iou 0.5 \
  --output outputs/tracking-evaluation.json
```

The evaluator reads local files only, class-gates each match and uses **maximum-IoU Hungarian one-to-one matching** (unmatched GT gets an extra dummy slot). Output contains overall and per-scenario `TP`, `FP`, `FN`, precision/recall/F1, ID switches, fragmentation counts, per-frame metrics and capped diagnostic events.

- **ID Switch (experimental):** previously matched GT ID is matched to a **different** predicted Object ID when visible again. A switch on return after a fully skipped occluded frame is counted at reappearance.
- **Fragmentation (experimental):** visible GT is unmatched in an evaluated frame, then later matched again; one sequence of unmatched-visible frames counts as one fragmentation.
- **FN:** missing matching prediction for a visible GT target. It does not alone distinguish a bad detector from a bad association threshold.
- **FP:** predicted object unmatched to a visible GT target. Bad / missing manual annotations can inflate FP.

These are **not** official CLEAR MOT IDSW, MOTA, IDF1, HOTA or TrackEval scores. To publish comparable MOT metrics, run a recognized evaluator (for example [TrackEval](https://github.com/JonathonLuiten/TrackEval)) with an appropriate annotation protocol and sequence split. Ground-truth quality matters more than a superficially low ID-switch count.

## Interpreting results and when to try stronger trackers

| Observed evidence | First experiment | Reason |
|---|---|---|
| Frequent visible-target FN with stable IDs when detected | Improve detection labels, confidence threshold, lighting and segmentation first | A tracker cannot recover all missing detector evidence |
| Fragmentation across brief partial occlusion | Compare **ByteTrack** against the same detector and frames; test low-score association and `track_buffer` | ByteTrack can reuse lower-confidence boxes for recovery |
| ID switches when similar-looking objects cross or reappear | Compare **BoT-SORT**, first without ReID, then optionally with ReID if appropriate | Camera compensation and appearance cues may help but cost runtime |
| Camera movement dominates | Evaluate BoT-SORT with/without global motion compensation on the same set | Plain 2D IoU assumes a fairly stable image plane |
| Single-frame alignment looks good, but 3D position jumps | Validate depth quality, calibration and time alignment independently | Better 2D tracking does not fix inconsistent depth units |

Official upstream algorithm references: [Ultralytics track mode](https://docs.ultralytics.com/modes/track) (available trackers and YAML parameters) and [TrackEval](https://github.com/JonathonLuiten/TrackEval). If an installed runtime exposes only some tracker types, check its version rather than assuming newer tracker options are available.

**Decision gate:** Compare methods with the *same* labeled test set, detector version, confidence settings, scene mix, compute device and documented real-frame sampling. Report both tracking quality and latency. No fixed IDSW/Recall threshold is credible without a target use case and a sufficient number of real labeled cases. Retain experimental status and unchanged defaults until the relevant real-data acceptance gates pass.
